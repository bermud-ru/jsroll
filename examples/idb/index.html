IndexedDB — IDB / IDBmodel

Пример по мотивам офлайн-справочника из проекта medicallabs2022 (там так же создаётся app.db = new IDB('db', N), к нему через db.bind(IDBmodel(...)) привязываются модели-хранилища со своими индексами, а данные читаются через model.getAll()/model.scope()). Здесь — упрощённый, но рабочий и самодостаточный вариант: два хранилища («Анализы» и «Пациенты») с индексами, без реального сервера.

Каждый блок ниже — самостоятельный пример одного аспекта API: инициализация, создание таблицы (схемы), заполнение данными, просмотр всех таблиц, запрос с фильтром по индексу. Открывайте по порядку — 2-й блок не сработает без 1-го и т.д. Внизу — статус/журнал событий и важное замечание про особенность библиотеки, на которую я наткнулся при проверке этого примера.
1. Инициализация — new IDB(name, version)

Открывает (или создаёт) базу IndexedDB в браузере.

var db = new IDB('medicallabsDemo', 1);
// … db.bind(...) для каждой таблицы, см. блок 2 …
db.connect();
db.onready(function () { /* база готова к работе */ });
2. Создание таблицы — IDBmodel(name, primaryKey, schema)

Схема хранилища объявляется функцией schema(db, tx), которая выполняется один раз при создании/повышении версии базы (onupgradeneeded) — здесь же создаются индексы.

Ожидание подключения (блок 1)… 
db.bind(IDBmodel('analyses', 'id', function (db, tx) {
    var store = db.objectStoreNames.contains('analyses')
        ? tx.objectStore('analyses')
        : db.createObjectStore('analyses', { keyPath: 'id', autoIncrement: true });
    if (!store.indexNames.contains('category')) {
        store.createIndex('category', 'category', { unique: false });
    }
}));
db.bind(IDBmodel('patients', 'id', function (db, tx) { /* аналогично, индекс по 'phone' */ }));
3. Заполнение таблицы данными — model.add(rows, opt)

Массовая вставка: один вызов add() с массивом объектов.

db.models.analyses.add([
    {code:'OAK', name:'Общий анализ крови', category:'Кровь', price:450},
    {code:'BIOCH', name:'Биохимия крови', category:'Кровь', price:1200},
    // …
], {
    done: function (e) { console.log('вставлено, id-шники:', e.result); },
    fail: function (e) { console.error(e); }
});
4. Демонстрация всех таблиц — db.models + model.getAll()

db.models — обычный объект «имя таблицы → модель», можно перебрать Object.keys(db.models).

Object.keys(db.models).forEach(function (name) {
    db.models[name].getAll({ done: function (e) { /* e.result — массив строк */ } });
});
5. Запрос с фильтром — getAll({index, keyRange})

Выборка по значению ИНДЕКСА (не полное сканирование таблицы) — то же, чем в medicallabs2022 пользуется model.scope({keyRange, index, done}). 

db.models.analyses.getAll({
    index: 'category',
    keyRange: 'Кровь',           // «сырое» значение — саму IDBKeyRange модель строит сама
    done: function (e) { /* e.result — только строки с category === 'Кровь' */ }
});
Журнал событий
    Особенность библиотеки, обнаруженная при проверке этого примера: внутри IDB.prototype.store() (см. jsroll.js) для операций чтения (get/getAll/count/filter/paginator) объект хранилища открывается как tx.objectStore($.tables), то есть передаётся МАССИВ имён таблиц модели, а не строка. Для модели с ОДНИМ хранилищем (как в обоих примерах здесь и в medicallabs2022) это на практике работает, потому что браузер приводит нестроковый аргумент к строке через Array.toString(), а у массива из одного элемента это даёт ту же строку без изменений. Но для модели, объявленной сразу на НЕСКОЛЬКО таблиц (IDBmodel(['a','b'], …)), тот же код превратится в строку "a,b", которая ни одному хранилищу не соответствует — чтение сломается. Итог: с одно-табличными моделями (обычный случай) всё работает; с много-табличными — на операциях чтения стоит перепроверить.
